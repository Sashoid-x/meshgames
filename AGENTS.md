# MeshGames — Unified Agent Guide

<role>
Ты — инженер по Android/Kotlin, работающий над MeshGames: 5 классических
игр поверх сети Meshtastic без интернет-сервера. Ты держишь протокол
доставки, логику сессий и UI в синхроне с `docs/PROTOCOL.md`, проверяешь
каждое изменение тестами до того, как сообщить о готовности, и считаешь
полевые логи с реальных устройств главным источником истины о радиоканале.
</role>

<context_and_memory>
- **Цель проекта:** обмен минимальными кадрами между двумя телефонами по
  радио. Единственный транспорт — TCP-клиент локального «Mesh Bridge» форка
  Meshtastic-Android (`127.0.0.1:8090`, portnum моста — настраивается в
  форке, дефолт 69 SIMULATOR_APP, `want_ack=false`; оба телефона обязаны
  совпасть по portnum). TAK-петля, TCP-клиент и `portnum=333` удалены — их
  не воскрешать; тесты транспорта лежат в `net/bridge/`.
- **Синхронизация приложения (`app`) и автономного сервера (`bot_server`):**
  Сервер и Android-приложение ОБЯЗАНЫ быть ВСЕГДА строго синхронизированы по протоколу,
  форматам кадров, расписаниям, движкам игр и структурам данных. Код `game/` и `net/`
  подключен в `bot_server` напрямую через symlink к `app/src/main/kotlin/com/meshgames/`.
  Любые изменения протокола/кодеков обязательно проверяются тестами обоих модулей:
  `./gradlew :app:testDebugUnitTest :bot_server:test`.
- **Источник истины по протоколу:** `docs/PROTOCOL.md`. `README.md` —
  обзор и UX; при расхождении верить PROTOCOL.md.
- **Референс Meshtastic-Android** (`/home/sash/opencode/Meshtastic-Android`) —
  **только чтение** (сертификаты, примеры кода). Никогда не изменять.
- **Git-репозиторий:** проект версионируется в git (ветка `main`). Результат работы =
  зафиксированные изменения, собранный APK + fatJar и чёткий отчёт.
- **Полевые логи:** пользователь кладёт файлы `meshgames-<hex clientId>-*.log.txt`
  в рабочую папку. Формат строки: `MM-dd HH:mm:ss.SSS [TAG] msg`.
  Теги: `APP` (граф, link), `S` (сессии/диспатч), `TX`/`TX*`
  (отправка/повтор), `RX` (приём + причины пропуска/дубликата),
  `BR` (соединение, TX/RX сокета, фильтры, presence),
  `NET` (ошибки отправки), `LOG` (служебное). Имя файла содержит clientId в hex — тот же, что в поле
  `from` кадров моста; `packets.json` из форка Meshtastic (он большой, ~6 МБ
  — только grep/фильтры, не читать целиком).
- **Диагностика в приложении:** `com.meshgames.debug.DebugLog` — кольцевой
  буфер (последние 500 строк) + файл
  `Android/data/com.meshgames/files/meshgames-<clientId>.log` (ротация 1 МБ).
  Панель «▶ дебаг» по умолчанию **скрыта**: включается Настройки →
  Диагностика и рисуется полупрозрачным оверлеем поверх экрана (макету и
  доскам не мешает): копирование всего лога, экспорт в «Загрузки», очистка.
  Новые точки диагностики добавлять через `DebugLog.d(tag, msg)` — сообщения
  короткие, по-русски.
</context_and_memory>

<protocol_invariants>
Нарушение любого из этих пунктов — регрессия, даже если тесты зелёные:

- **Envelope:** `[0]=0x47, [1]=2 (единственная версия), [2]=type,
  [3]=0 (резерв, не трогать!), [4..5]=sessionId LE, [6..7]=seq LE,
  [8..11]=cumAck u16 LE + bitmap u16 LE` — заголовок всегда 12 байт;
  `cumAck=0xFFFF` при пустом bitmap — сентинел «ничего не подтверждено»
  (приёмник игнорирует). MsgType: INVITE=1, INVITE_RESP=2,
  MOVE=3, SHOT=4, SHOT_RESULT=5, id 6 свободен (легаси-ACK удалён),
  SYNC_REQ=7, SYNC_RES=8, GAME_OVER=9, DRAW_OFFER=10, DRAW_RESP=11,
  INVITE_CANCEL=12, READY=13, SESSION_CLOSE=14, SESSION_DELETE=15, ACK_ONLY=16, BATCH=17.
  INVITE строго `[gameTypeId][inviterSide]` или `[gameTypeId][inviterSide][difficulty]` — однобайтовый не принимается.
- **Доставка «повторяй и не жди»** (`ReliableChannel`): фиксированные
  оптимизированные расписания — обычные кадры `RETRY_GAPS_MS=[6,10,16,30,60]` с
  (6 отправок, 0..122 с — первый гэп 6с вместо 4с предотвращает преждевременные повторы
  и полудуплексные коллизии на LoRa с RTT 4-5с; в норме ответный ход пира гасит повторы
  до 6с, экономя 50% трафика), критичные
  `INVITE/INVITE_RESP/INVITE_CANCEL/READY/GAME_OVER/SESSION_DELETE` —
  `PATIENT_RETRY_GAPS_MS=[8,14,25,45,60]` с (6 отправок, 0..152 с; первый гэп 8с
  дает игроку время увидеть уведомление и нажать кнопку). После базового
  расписания непОДТВЕРЖДЁННЫЙ игровой кадр **не забывается**, а переходит в вечный
  режим `ETERNAL_GAP_MS=120_000` (по одному пакету/2 мин, ровно один за
  тик) — до piggyback-подтверждения пира либо очистки канала; рестарт
  восстанавливает такие кадры тоже в вечном режиме (полевой инцидент
  18.10 sid=17753: «сгоревшие» до возвращения пира `SESSION_CLOSE`/
  `SYNC_REQ` оставили ему вечную дырку в `rxNext` — весь поток оседал в
  стэше, партия висла с откатами каждые 5 мин).
  **Терминальные кадры (`GAME_OVER`, `SESSION_DELETE`, `INVITE_CANCEL`) в вечный режим НЕ переходят:**
  после 6 отправок (152 с) они удаляются из очереди, исключая бесконечный спам в эфир.
  Приём `GAME_OVER` немедленно гасится ответным `ACK_ONLY` (12 байт, seq=0).
  Приём любого кадра для неизвестной/удалённой сессии отвечает `SESSION_DELETE` (cooldown 30с),
  что немедленно останавливает повторы у пира.
  `tick()` догоняет пропущенные тики (абсолютное расписание;
  в вечном режиме — один повтор за тик, сон не плодит взрыв пакетов).
- **Никакого ожидания подтверждений:** standalone ACK-кадров в протоколе
  нет вовсе (MsgType.ACK удалён); подтверждение — только piggyback
  `cumAck` в заголовке любого исходящего кадра (сентинел `0xFFFF` —
  «ничего не подтверждено», приёмник его игнорирует). Никакого
  backoff и «ждём подтверждения с обеих сторон» — на реальном LoRa-пути
  это вешало оба аппарата.
- **Дедуп приёма:** `rxNext` + стэш out-of-order; дубликат не порождает
  трафика и не меняет состояние.
- **`SESSION_DELETE` — мимо канала** (ранняя ветка в `handleIncoming` до
  `channel.receive`): удаление срабатывает даже при «дырке» в seq; повторы
  идемпотентны. `deleteSession`/`dismiss` удаляют сессию **сразу**; кадры
  продолжает переотправлять «сиротская» очередь `repeats` в SessionManager.
- **`SYNC_REQ`/`SYNC_RES` — мимо порядка** (ветка в `handleIncoming` до
  `channel.receive` → `ReliableChannel.receiveOutOfBand`): «дырка» ниже seq
  не блокирует исцеление (полевой deadlock sid=40290). Кадр отдается сразу,
  seq помечается в `deliveredEarly` — дедуп гасит повторы, `rxNext`
  «проглатывает» его при закрытии дырки, а `ackSnapshot()` видит его в
  `bitmap` (пир гасит повторы раньше расписания). `deliveredEarly` чистится
  в `clear()`/`restore()`. **`SYNC_RES` отвечается только из покоя**: движок
  в непокое (в морском бое — `pendingShot != -1`) молчит — иначе соперник
  (в покое) сравнивает дайджест «до применения результата» со своим и
  объявляет ложный SYNC_CONFLICT (полевая гонка 17.10 sid=13951: `SHOT` шёл
  131 с, `SYNC_REQ` пришёл раньше `SHOT_RESULT`). Молчание безопасно —
  повторы `SYNC_REQ` позже попадают на покой и получают честный дайджест.
- **Лечение зависшего выстрела** (`SessionManager.tick` →
  `healStuckPendingShot`): `pendingShotSinceMs` ставится в `submitMove`
  (Shoot) и лениво при первом тике (restore-случай), сбрасывается в покое;
  по таймауту `PENDING_SHOT_TIMEOUT_MS=300_000` движок обязан вернуть
  `abandonPendingShot()==true` (морской бой: pendingShot сбрасывается, в
  дайджест не входит), затем `sendSyncRequest` **без** инкремента
  `localActivity`. Далее — честный исход: дайджесты разошлись →
  `SYNC_CONFLICT`, сошлись → партия продолжается. Лечится только активная
  незакрытая сессия (в `closed` таймер копится, но не шлёт трафик).
- **Дуп-INVITE:** повторный `INVITE` при `inviteAnswered` обрабатывается
  **до** дедупа → новый ненадёжный `INVITE_RESP`; `clearUnacked()` при
  отказе и `cancelInvite` бросают расписание `INVITE`.
- **Балда: спор симметричен и не блокирует партию** (движок `BaldaEngine`,
  payload'ы в PROTOCOL.md §6): слово вне словаря ложится условно
  (`KIND_WORD_DISPUTED=0x81`), очередь хода НЕ уходит; вердикт
  (`[0x03][verdict]` кадром MOVE вне очереди хода) даёт только не
  двигавшая букву сторона (`pendingVerdict` = `dispute.mover != mySide`).
  Состояние спора входит в digest и engineState — рестарт дорешивает спор
  (полевой принцип «никогда не жди»: спор без вердикта не вешает игру,
  повторы закрываются journal-resend и вечными повторами). Словарь —
  `GameEngines.wordChecker`, подставляется в `AppGraph.init` **до**
  создания `SessionManager` (иначе restore сессий получит заглушку и
  стартовое слово разойдётся с пиром). Стартовое слово — детерминированная
  функция sid от `checker.startWords()`; **повтор любого уже сыгранного
  слова, включая стартовое и любые формы с взаимозаменяемыми буквами е/ё, и/й, ь/ъ, отклоняется на обеих сторонах до отправки**
  (иначе digest'ы разъезжаются). Парные буквы е/ё, и/й, ь/ъ при проверке
  словаря взаимозаменяемы (перебор вариантов ≤2^10 — чистая
  детерминированная функция, обе стороны решают одинаково; на поле и в
  выборе — канон: е, и, ь). UI не предлагает вариантов слов из словаря
  (давало игру перебором): выбор буквы — таблица 6×5 поверх поля (пары в
  одной клетке), буква лежит на поле полутоном до подтверждения, затем
  змейка по клеткам; управление только тапами по доске (кнопок нет):
  повторный тап по последней клетке пути — отправка, тап по первой —
  сброс пути, долгий тап по новой букве — убрать её. Букву ставят только
  в клетку, соседнюю с занятой (движок гарантирует структурой — путь
  через «глухую» клетку не построить; UI не даёт её выбрать); слово вне
  словаря перед спором спрашивает игрока — диалог «Отмена/Отправить»
  (`BaldaEngine.wordInDictionary` — предпросмотр той же мягкой проверки),
  спор уходит только по подтверждению. Список слов (два столбика «Имя:
  счёт» + слова) занимает всё место под доской; в альбоме — как в
  морском бое: слева доска, справа счёт и слова (тоже два столбика).
  Стартовое слово в списке не показывается — оно видно на поле.
  Пропуск хода входит в список слов/дайджест/состояние пустой записью
  (`len=0`, `passed=true`) — обе стороны видят его одинаково: таблица
  счёта рисует красное «Пропуск +0», а если последнее действие — пропуск
  соперника, в ряду над доской горит красная плашка «Соперник пропустил
  ход» (без неё пропуск незаметен — просто меняется «ваш ход»).
- **Дурак: скрытая информация — детерминизм, не кадры** (`gameTypeId=6`,
  движок `DurakEngine`, payload'ы в PROTOCOL.md §6): обе стороны считают
  раздачу из sid (xorshift32, прецедент — стартовое слово балды), в эфир
  идут только действия; чужая руна не рисуется — уровень UI. Канон
  правил закреплён: 36 карт, ПОДКИДНОЙ — стол захода накапливает пары
  «атака/бой» до 6; подкидывание — по номиналу ЛЮБОЙ карты захода (и
  атаки, и боя), только от атакующего, пока атак < 6 и защитнику есть
  чем ответить; начальный атакующий — младший козырь (равенство —
  младшая карта вообще); бой — той же масти старше либо козырь, бой
  6-й атаки — авто-бито; «хватит» только когда все забиты; бито — весь
  заход в сброс, роли меняются (атакующий следующим — защитник);
  взятие — берущий забирает ВСЕ карты захода, атакующий остаётся;
  добор до 6 первым — атакующий; колода пуста → без карт вышел, последний
  с картами — дурак (`LAST_WITH_CARDS`, winner — вышедший), оба вышли —
  ничья (`BOTH_OUT`). State v3 (`DurakEngine.STATE_VERSION = 3`), прежнее
  состояние нечитаемо — движок создаёт заново из sid (у обеих обновлённых
  сторон раздача одинакова). Лог в engineState не входит (как у балды). UI:
  `PlayingCard` в Boards.kt, `DurakPanel` в GameScreen; кнопки «Беру»
  (защитник) и «Хватит» (забитый заход, в т.ч. при пустой руке атакующего),
  подсветка бьющих карт из `snapshot.legalBeats` и подкидываемых из
  `snapshot.legalThrows`.
- **Финал партии — поле остаётся на экране.** После GAME_OVER экран не
  закрывается и не перекрывает доску: финальная позиция + крупный итог
  (`resultText`, глазами `mySide`) и две кнопки в потоке макета (не
  оверлеем): «Ещё раз» — `GameViewModel.playAgain()`
  (`manager.invite` тому же сопернику той же игры → навигация на новую
  сессию; старая партия остаётся в списке) и «Закрыть» — `dismiss()`.
- **Случайные стороны:** `InvitePayload = [gameTypeId][inviterSide]`
  (0 = A, 1 = B) — цвета
  решаются случайно при каждом приглашении (`sideDecider` в SessionManager,
  в приложении — `Random`, в тестах — детерминированно), приглашённый
  занимает противоположную сторону. Повторы INVITE (`retryInviteIfStuck`)
  несут ту же сторону. Сторона A ходит/стреляет первым в движках.
- **`retryInviteIfStuck`:** сессия в `INVITING` + `pendingCount()==0` →
  переотправка `INVITE` с переиспользованным `seq=0`
  (`ReliableChannel.send(forceSeq=0)`, указатель `nextSeq` не откатывается).
  Вызывается из `restore()` и при открытии GameScreen; идемпотентен.
  Экран `INVITED` обязан иметь кнопки «Принять»/«Отклонить» (диалог после
  рестарта не восстанавливается).
- **Итог партии — всегда глазами `mySide`** (`resultText(result, sess.mySide)`):
  `GameResult.winner` — абсолютная сторона (A/B), а игрок видит
  «победа/поражение». Доска показывает только факты (знаки/фигуры); любая
  оценка «кто выиграл» обязана идти через `sess.mySide` — жёстко Side.A даёт
  инвертированный вердикт второй стороне (полевой отчёт 20.10: «выиграл
  ноликами, на доске поражение»). Сторону показывать игроку явно: шахматы и
  шашки переворачиваются, морской бой и крестики-нолики — нет, поэтому у TTT
  есть подпись «вы — ✕/○»; без неё игрок принимает чужую фигуру за свою.
  Доски с абсолютной разметкой (`cells`: 1 = ✕ сторона A, 2 = ○ сторона B)
  обязаны совпадать с `GameResult.winner` — покрыто тестом
  `BotAgentTest.humanIsNoughtsAndResultMatchesAbsoluteBoard` и
  `ResultTextTest`.
- **Доска 8×8 — как на настоящей доске**: a1 тёмная, a8 светлая и у шахмат,
  и у шашек (`isLight = (r + c) % 2 == 0`, r = 0 — 8-я горизонталь). В шашках
  шашки стоят на тёмных клетках, поэтому расстановка
  `CheckersEngine.setupInitial` заполняет `(r + c) нечёт` — белые начинают на
  a1, c1, e1, g1. Эталон — `board.png`. Смена этого расклада (даже «чисто
  визуальная») меняет начальную позицию и делает старые/новые сборки
  несовместимыми **именно в шашках** — правку сопровождать подъёмом версии
  и проверкой на двух аппаратах. Расклад зафиксирован и в версии состояния:
  `CheckersEngine.STATE_VERSION` (сейчас 2), состояние прежней версии
  нечитаемо — сохранённая такая партия начинается заново с начальной
  позиции (у обеих сторон, обновивших APK, одинаково; лог
  «состояние sid=… нечитаемо — движок создан заново»).
- **Шашки: несколько маршрутов в одну клетку — выбор за игроком.** Русские
  шашки не требуют максимального взятия, а шашка, пришедшая на последнюю
  горизонталь при взятии, немедленно становится дамкой и продолжает бой —
  поэтому в одну клетку могут вести разные цепочки.
  `CheckersEngine.routes(dest)` возвращает их список, `commitAt(dest, routeIndex)`
  применяет выбранную; в UI это кнопки ◀ ▶ и счётчик «1/2», а все ветви
  рисуются «змейками» на доске (выбранная — яркая оранжевая, остальные
  приглушённые), чтобы было видно, через какие площадки идёт каждый вариант.
  Молча отдавать первую ветвь нельзя (полевой скриншот 20.10: в клетку вели
  коротая и длинная цепочки, игроку показали только длинную). Состав цепочки
  в payload не входит — пир валидирует её сам: кадр — только площадки
  приземления (`[n, sq…]`), легаси-формат «откуда, побита, площадка…» удалён.
- **Тестовый бот** (`game/session/BotAgent`, настройка «Тестовый бот»):
  принимает **все** входящие приглашения, расстановку подтверждает сразу,
  на ничью и на спор балды отвечает «да», сам игры не инициирует. Ход
  подбирает движок: `GameEngine.botMove(): MoveInput?` (null — чужой ход /
  финиш / спор), дальше штатный `submitMove` через
  `SessionManager.submitBotMove`. Шагает раз в секунду после `manager.tick()`
  в тике AppGraph; при выключенном настройке шаг пустой. Сложности нет —
  бот нужен, чтобы держать партию в правилах, пока человек проверяет связь
  с расстояния. Протокол бот не меняет; UI подавляет диалог приглашения,
  уведомление, диалог ничьей и диалог вердикта (`SettingsStore.botEnabled`,
  в полевых логах — тег `BOT`).
- **Валидация ходов** движком на обеих сторонах: нелегальный локальный ход
  не отправляется, полученный — отклоняется с `SYNC_REQ`; конфликт
  синхронизации завершает партию (`SYNC_CONFLICT`).
- **Кадр моста:** `[u32 len LE][u32 from LE][u32 to LE][body]` (len = 8 +
  body.size ≤ 220; ping — len=0). От моста к клиенту перед wrapper'ом идёт
  LoRa-заголовок `[u32 loraFrom][u32 loraTo]` — он игнорируется: маршрутизация
  живёт в `from`/`to` внутри wrapper'а (clientId — случайный u32 в pref-ключе
  `tak_client_id`, ключ **сохранён намеренно** — смена сломает узнаваемость
  телефона; clientId ≠ номер узла LoRa **у существующих установок**).
  `body[0]=0x47` → envelope целиком (его собственный magic, **не срезать**),
  `0x50` → presence `[0x50][ver=1][busy u8][nameLen u8][name UTF-8 ≤ 32]`,
  `0x49` → HELLO `[0x49][ver=1][nodeId u32 LE][nameLen u8][name ≤ 32]` —
  служебный кадр «мост → клиент» с номером и именем СВОЕЙ ноды (всегда с
  нулевым LoRa-заголовком, иначе старый APK оборвёт соединение; формат —
  PROTOCOL.md §5, доработка форка — `meshbridge-hello-prompt.md`),
  `0x53` → STAT_BROADCAST `[0x53][ver=1][gameTypeId u8][sid u16 LE][winner u8][reason u8][playerA u32 LE][playerB u32 LE]`
  (15 байт body, 23 байта с wrapper'ом) — широковещательный кадр (to=0) результата завершенной игры для сервера статистики.
- **Маршрутизация и фильтры эфира (защита от шума и битых кадров):**
  1. Эхо своих пакетов (`from == myId`) отсекается на уровне сокета/клиента ноды.
  2. Игровые кадры чужих сессий (`to != 0 && to != myId`) игнорируются ботом и клиентом.
  3. В `SessionManager.handleIncoming` передаются ТОЛЬКО кадры с `body[0] == 0x47` (Game Envelope).
     Кадры presence (`0x50`), статистики (`0x53`) и HELLO (`0x49`) обрабатываются соответствующими
     менеджерами и ни в коем случае не скармливаются в Envelope.decode (иначе в лог летит ложный «битый кадр»).
- **Статистика и команда `!table`:**
  Сервер (`bot_server`) собирает результаты игр в `bot_data/stats.json` с дедупликацией по
  `(sessionId, gameTypeId, playerA, playerB)`. Консольная команда `table` (`t`) выводит форматированную
  таблицу лидеров и историю игр. При получении текстового сообщения `!table` или `!таблица`
  (`PortNum.TEXT_MESSAGE_APP = 1`) в канале Meshtastic, сервер транслирует краткую сводку в канал.
  Длина ответа СТРОГО ограничена: $\le 100$ символов кириллицы ($\le 200$ латиницы / $\le 200$ байт UTF-8).
- **Идентичность (`app/ClientIdentity.kt`):** обновившиеся установки
  **сохраняют** свой `tak_client_id` навсегда (инвариант узнаваемости);
  свежая установка/переустановка стартует на временном id с pref-флагом
  `tak_client_id_pending` (переживает рестарты), первый HELLO закрепляет
  `id = nodeId` и снимает флаг; старый форк без HELLO → прежнее поведение
  (временный id сохраняется и живёт). Имя игрока: своё `player_name` →
  имя ноды из HELLO → заглушка `Игрок-XXXX`.
- **Мост шлёт portnum (дефолт 69 SIMULATOR_APP, настраивается в форке) с
  `want_ack=false`** — firmware-ретрансмитов нет,
  каждый кадр расписания занимает ровно один эфирный слот; экономия эфира
  только числом пакетов, поэтому пакеты минимальные, а лишние повторы
  недопустимы.
- **Для связи нужен форк** Meshtastic-Android с включённым Mesh Bridge на
  одном канале на обоих телефонах — TAK-путь из приложения удалён,
  штатное (стоковое) приложение не поддерживается.
</protocol_invariants>
