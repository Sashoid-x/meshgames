# Протокол MeshGames

Игровые сообщения MeshGames идут TCP-кадрами через локальный «Mesh Bridge»
форка Meshtastic-Android (единственный транспорт приложения) и попадают
в эфир LoRa пакетами portnum моста (настраивается в форке, дефолт 69) —
см. секции 1 и 5.

## 1. Транспортный уровень (TCP-мост)

Приложение общается с локальным «Mesh Bridge» форка Meshtastic-Android
(`127.0.0.1:8090`, plain TCP — loopback, TLS не нужен; включается в
приложении Meshtastic: Settings → Radio Config → Mesh Bridge, там же выбор
канала вещания и portnum). Мост транслирует полезную нагрузку broadcast'ом
в эфир (свой portnum, `want_ack=false` — см. секцию 5; оба телефона должны
использовать одинаковый portnum).

Кадр в TCP-потоке (little-endian):

```
[u32 len][u32 from LE][u32 to LE][body…]     len = 8 + body.size
```

| Поле | Значение |
| --- | --- |
| `from` | мой clientId (u32, стабилен для устройства; у существующих установок — прежний случайный id навсегда, у свежих после HELLO — номер ноды LoRa; см. «Идентичность» в секции 5) |
| `to` | получатель (0 — broadcast; мост всегда вещает broadcast'ом) |
| `body` | `0x47` + envelope (игровой кадр), presence-блоб `0x50`, широковещательная статистика завершения партии `0x53` (секция 8); `0x49` — HELLO от моста (только мост → клиент, секция 5) |

- адресация MeshGames живёт в wrapper'е `[from][to]` внутри payload — мост
  о ней не знает; при приёме из эфира мост добавляет перед wrapper'ом
  заголовок LoRa `[u32 loraFrom][u32 loraTo]`, который MeshGames игнорирует;
- кадр `len = 0` — ping (keepalive TCP);
- лимит wrapper — 220 байт (payload моста), envelope ≤ 212 байт;
- фильтры приёма (по recipient и self-фильтр по sender) — в
  `BridgeTransport.handleFrame`.

Примечание: наш мост шлёт пакеты с `want_ack=false` — firmware-ретрансмитов
нет, каждая отправка занимает ровно один эфирный слот. Страховка доставки —
наш протокол (секция 3); экономия эфира — числом пакетов (минимальные
payload, отсутствие отдельных ACK-кадров, умеренный presence).

## 2. Envelope

Каждый payload — envelope. Заголовок один (12 байт):

```
[0]      magic   = 0x47
[1]      version = 2
[2]      type    (MsgType)
[3]      flags   = 0
[4..5]   sessionId u16 LE
[6..7]   seq      u16 LE
[8..9]   cumAck  u16 LE   — подтверждено всё до seq включительно
[10..11] bitmap  u16 LE   — бит i = принят seq cumAck+1+i
[12..]   payload типа сообщения
```

Каждый кадр несёт кумулятивное подтверждение приходов от соперника прямо
в заголовке — отдельные эфирные ACK-пакеты нами не порождаются вовсе
(см. секцию 3). Значение `cumAck = 0xFFFF` при пустом `bitmap` — сентинел
«ничего не подтверждено» (честное значение до первого прихода): приёмник
его игнорирует и не снимает ни одного кадра отправителя. Ранние версии
заголовка (v1, 8 байт) из протокола удалены — кадр с иным `version`
отбрасывается целиком.

`sessionId` генерирует инициатор и одинаков у обеих сторон.
`seq` — порядковый номер кадра **внутри сессии** (направление: я → соперник);
учитывается wrap-around u16.

### Типы сообщений

| id | Тип | Payload |
| --- | --- | --- |
| 1 | INVITE | `[gameTypeId][inviterSide]` или `[gameTypeId][inviterSide][difficulty]` (inviterSide: 0 = A, 1 = B; difficulty: 0 дефолт, 1 лёгкий, 2 средний, 3 сложный) |
| 2 | INVITE_RESP | `[accepted]` (1/0) |
| 3 | MOVE | зависит от игры (секция 6) |
| 4 | SHOT | `[coord]` (морской бой) |
| 5 | SHOT_RESULT | `[coord, res]`, res: 0 промах, 1 попадание, 2 убит |
| 7 | SYNC_REQ | хвост журнала ходов (опционально; секция 4) |
| 8 | SYNC_RES | `[cumAck u16][turn][status][digest u16]` + хвост журнала (опционально; секция 4) |
| 9 | GAME_OVER | `[winner][reason]`: winner 0=A, 1=B, 2=нет; reason — ordinal `ResultReason` |
| 10 | DRAW_OFFER | пусто |
| 11 | DRAW_RESP | `[accepted]` |
| 12 | INVITE_CANCEL | пусто |
| 13 | READY | пусто (морской бой: расстановка подтверждена) |
| 14 | SESSION_CLOSE | `[closed]` (1 — игра закрыта с сохранением, 0 — возобновлена) |
| 15 | SESSION_DELETE | пусто (сессия удалена у инициатора — удалить у себя) |
| 16 | ACK_ONLY | пусто (seq=0, легковесный кадр 12 байт с piggyback-ACK для гашения повторов пира) |
| 17 | BATCH | `[count][len0][sub0][len1][sub1]…` (составной пакет из нескольких envelope'ов в одном LoRa-слоте) |

Сторона A ходит/стреляет первым. Кто из игроков займёт сторону A —
решается случайно при каждом приглашении: инициатор занимает выбранную
сторону и передаёт её байтом `inviterSide` в INVITE, приглашённый
получает противоположную. INVITE строго `[gameTypeId][inviterSide]` —
кадр в один байт (ранняя версия) не принимается; id MsgType 6 (легаси-ACK)
свободен и переиспользоваться не будет. `gameTypeId` — отдельное
пространство имён payload'а: 1 крестики-нолики, 2 шашки, 3 шахматы,
4 морской бой, 5 балда, 6 дурак; неизвестный id → приглашение
игнорируется (APK без дурака приглашение не поймёт — волной обновляются
оба аппарата).

## 3. Надёжная доставка («повторяй и не жди»)

Схема намеренно НЕ ждёт подтверждений: на реальном LoRa-пути отдельные
ACK-кадры возвращались ненадёжно, обе стороны зависали во взаимном ожидании
(«кадры ждут подтверждения»), а эфир забивался ретрансмитами. Теперь:

Каждое сообщение (кроме ненадёжных — см. ниже) идёт с seq. Приёмник:

- ведёт `rxNext` — ожидаемый seq;
- применяет кадр **ровно один раз**: дедуп по seq (повтор безопасен),
  out-of-order кадры складываются в стэш (до 32) и применяются, когда
  заполнится дырка;
- подтверждает принятые кадры **только piggyback'ом**: заголовок каждого
  исходящего кадра несёт `cumAck = rxNext - 1` (все seq ≤ cumAck получены)
  + `bitmap` — 16 бит для полученных out-of-order кадров выше cumAck;
  до первого прихода уходит сентинел `cumAck = 0xFFFF` («ничего не
  подтверждено»), приёмник его игнорирует. Отдельных ACK-кадров в
  протоколе нет вовсе (MsgType удалён) — получатель ничего не «должен»;
- `SESSION_DELETE` обрабатывается мимо канала: удаление должно сработать,
  даже если в seq есть «дырка» или после рестарта счётчики разошлись;
- `SYNC_REQ`/`SYNC_RES` доставляются **мимо порядка** (`receiveOutOfBand`):
  дырка ниже seq не должна блокировать исцеление (полевой провал 16.10:
  потеря `SHOT`/`SHOT_RESULT` оставила дыру в `rxNext`, и `SYNC_RES` осел
  в стэше навсегда — взаимный deadlock `pendingShot`). Кадр применяется
  сразу; его seq помечается как отданный, и `rxNext` «проглатывает» его
  при закрытии дырки — ни повтор, ни позднее закрытие дырки не дают второй
  доставки. Дедуп и piggyback работают как обычно, отданный мимо порядка
  seq входит в `bitmap` (пир гасит его повторы раньше расписания).

Отправитель:

- шлёт кадр по фиксированному расписанию повторов (оптимизировано под RTT LoRa):
  - обычные игровые кадры (`MOVE`, `SHOT`, `DRAW_*`, `SYNC_*`,
    `SESSION_CLOSE`) — отправки на **0/6/16/32/62/122 с** (гэпы 6, 10, 16, 30, 60 с, 6 отправок,
    спан ~2 мин): первый гэп 6с (вместо ранних 4с) предотвращает преждевременные повторы
    и взаимные коллизии на LoRa, когда RTT канала составляет 4–5с. В нормальной партии
    ответный ход пира с piggyback-cumAck гасит расписание до 6с, устраняя дублирующий трафик (до 50% меньше эфирного шума);
  - handshake- и критичные (`INVITE`, `INVITE_RESP`, `INVITE_CANCEL`,
    `READY`, `GAME_OVER`, `SESSION_DELETE`) — **0/8/22/47/92/152 с** (гэпы 8, 14, 25, 45, 60 с,
    6 отправок); первый гэп 8с дает человеку достаточно времени увидеть уведомление и нажать кнопку без лишних повторов INVITE;
- по исчерпании базового расписания непОДТВЕРЖДЁННЫЙ игровой кадр **не забывается**,
  а переходит в вечный режим: повтор каждые **120 с** (`ETERNAL_GAP_MS`),
  по одному пакету на кадр — пока пир своим piggyback-`cumAck` не подтвердит
  получение либо канал не очищен (`clearUnacked`/`clear`/откат). Это
  спасает от вечной дырки в `rxNext` пира после парных рестартов/сна
  (полевой инцидент 18.10 sid=17753: «сгоревшие» до возвращения пира
  `SESSION_CLOSE`/`SYNC_REQ` оставили дырку, весь дальнейший поток —
  `SHOT_RESULT` в том числе — оседал в стэше, партия висла с откатами
  каждые 5 мин; цена вечного режима — обычно 0–3 пакета раз в 2 мин);
  **Исключение — терминальные кадры (`GAME_OVER`, `SESSION_DELETE`, `INVITE_CANCEL`):**
  они завершают партию или вызов, за ними нет последующих ходов, и они не могут оставить дыру
  для будущих кадров. После 6 попыток базового расписания (152 с) терминальные кадры
  удаляются из очереди и в вечный режим НЕ переходят, предотвращая замусоривание эфира;
- **Мгновенное гашение `GAME_OVER` через `ACK_ONLY`:** приём `GAME_OVER` (как первичного,
  так и повторов) немедленно подтверждается отправкой кадра `ACK_ONLY` (12 байт, seq=0),
  что сразу снимает кадр с переотправки у соперника;
- **Самоисцеление от рассинхронизации удалённых сессий:** приём любого пакета для неизвестной
  или уже удалённой локально сессии вызывает ответный `SESSION_DELETE` (с cooldown 30 с),
  что мгновенно очищает сессию на стороне пира и останавливает его цикл повторов;
- если тики пропускались (сон приложения), `tick` догоняет все просроченные
  повторы расписания за один вызов; в вечном режиме догон даёт **один**
  повтор за тик (nextDue сдвигается от «сейчас» — сон не плодит взрыв
  пакетов);
- при переотправке в заголовке обновляется свежий piggyback-ACK;
- piggyback от пира гасит расписание раньше срока: если ответный кадр и так
  идёт (ход, `INVITE_RESP`, `SHOT_RESULT`), повторы не нужны — бесплатная
  оптимизация. От неотвечающего пира ждать нечего: работает расписание;
- по piggyback-подтверждению отправитель **пассивно измеряет латентность**
  канала (от первой отправки погашенного кадра до прихода cumAck; рестарт
  обнуляет оценку). Это чисто информационный индикатор в UI (`~N с`),
  протокол и расписания от него не зависят;
- при рестарте восстанавливает счётчики и unacked; первый повтор уходит
  через один гэп после рестарта (без взрывной пересылки всего сразу),
  кадры с исчерпанным базовым расписанием восстанавливаются **в вечном
  режиме** (первый вечный повтор — через `ETERNAL_GAP_MS`): рестарт не
  «сжигает» непОДТВЕРЖДЁННЫЕ, иначе у пира навсегда остаётся дырка;
- `deleteSession` и `dismiss` удаляют сессию **сразу** (пользователь ничего
  не ждёт), а их кадры (`SESSION_DELETE`, прощальный `GAME_OVER`) продолжает
  переотправлять «сиротская» очередь вне сессии по тому же расписанию;
- ответ на отклонённое приглашение (`INVITE_RESP(принято=0)`) отправляется
  **ненадёжным** кадром (`sendFragile`, без seq): инициатор узнаёт об отказе
  с первого же пакета, в эфире — ноль повторов.

Потери/повторы на уровне канала не влияют на игру: дедуп по seq гарантирует
однократное применение каждого хода. Мост шлёт пакеты с `want_ack=false` —
firmware-ретрансмитов нет, каждая отправка расписания занимает ровно один
эфирный слот (на SF12 ~3 с); поэтому экономим дайти-цикл, держа общее
число пакетов минимальным.

## 4. Сценарии

### Приглашение

```
A → B  INVITE(gameType, seq=0)
B      уведомление: «Принять» / «Отклонить»
B → A  INVITE_RESP(принято=1)  → у A сессия ACTIVE (или PLACEMENT)
    или INVITE_RESP(принято=0) → у A CANCELLED, у B CANCELLED
A → B  INVITE_CANCEL (A отменил приглашение сам)
```

Повторный `INVITE` (наш ответ потерялся) обрабатывается в `handleIncoming`
**до** дедупа канала: если сессия уже отвечала (`inviteAnswered`), на дубль
уходит ещё один ненадёжный `INVITE_RESP` — инициатор переотправляет `INVITE`
по расписанию, и цепочка длится, пока один из ответов не долетит.

**Лечение «зависшего» приглашения.** Если `INVITE` исчерпал все попытки
(ответ не дошёл — например, приложение инициатора было закрыто), сессия
остаётся в `INVITING` навсегда: раньше она просто висела в «ждём ответа».
Теперь `retryInviteIfStuck` переотправляет `INVITE` (1) при восстановлении
сессии после рестарта и (2) при открытии сессии на экране игры; вызов
идемпотентен — пока в канале есть кадры в ожидании, он ничего не шлёт.
Переотправка **переиспользует seq=0** (`ReliableChannel.send(forceSeq=0)`),
поэтому счётчики обеих сторон остаются согласованными в обоих вариантах:
пир либо уже получил исходный `INVITE` (кадр идёт в дедуп, а дуп-INVITE-ветка
повторяет `INVITE_RESP`), либо не получил ни одного кадра (тогда `seq=0` для
него — первый). Ответ несёт `cumAck` и гасит расписание повторов сразу после
доставки. Аналогично, если приглашение было получено, но не обработано
(статус `INVITED` после рестарта), экран игры показывает кнопки
«Принять»/«Отклонить» — диалог после рестарта не восстанавливается.

### Игра

```
A → B  MOVE / SHOT            (валидация движком A до отправки)
B      валидация движком B при приёме; нелегален → SYNC_REQ вместо применения
B → A  SHOT_RESULT            (только для SHOT)
A      проверка: результат соответствует ожидающему выстрелу
```

Когда движок одной из сторон завершает партию (мат, все корабли уничтожены,
нет ходов…), она отправляет GAME_OVER; вторая сторона завершает по получении.

### Ничья и сдача

```
A → B  DRAW_OFFER;  B → A  DRAW_RESP(принято)  → ничья (обеим сторонам)
                        или DRAW_RESP(отклонено) → игра продолжается
A      сдача → A шлёт GAME_OVER(winner=B, RESIGN)
```

### Закрытие и удаление сессии

```
A → B  SESSION_CLOSE(1)   (пользователь закрыл игру)  → обе сессии closed=true,
                                             статус не меняется, ходы блокируются
A → B  SESSION_CLOSE(0)   (возобновление)             → closed=false, + SYNC_REQ
A → B  SESSION_DELETE     → B удаляет сессию, сообщает пользователю
                              («оппонент удалил партию») и предлагает новую игру
```

Сессия с `closed=true` остаётся на диске и **возобновляема**; локальные ходы
(`submitMove`/`checkersCommit`/`ready`) в закрытой игре блокируются на обеих
сторонах. `SESSION_DELETE` обрабатывается мимо канала: инициатор удаляет
сессию **сразу** (ничего не дожидаясь), а сам кадр ещё несколько раз уходит
в эфир из «сиротской» очереди; получатель удаляет её при первом же приёме,
повторы игнорируются.

### Синхронизация

SYNC_REQ → SYNC_RES(cumAck, turn, status, digest). Дайджест (u16) —
каноническая свёртка публичной части состояния движка. **Отвечает только
сторона в покое**: если движок не в покое (`pendingShot != -1`), `SYNC_RES`
вообще не отправляется — дайджест «в полёте» описывает состояние **до**
применения результата, а соперник в покое сравнил бы его со своим и объявил
ложный конфликт (полевая гонка 17.10 sid=13951: `SHOT` шёл 131 с, `SYNC_REQ`
пришёл раньше `SHOT_RESULT` — партия завершилась SYNC_CONFLICT при
фактически совместимых состояниях). Молчание безопасно: повторы `SYNC_REQ`
по расписанию позже попадают на покой и получают честный дайджест. Сравнение
дайджестов имеет смысл только **в покое** (в морском бое — `pendingShot == -1`)
и только если с момента отправки SYNC_REQ моё состояние **не менялось**
(ответ мог пересечься в пути с моим новым ходом — устаревший ответ не должен
давать ложный конфликт). В покое расхождение → сверка по журналу ходов
(см. ниже), и только если сверка невозможна — SYNC_CONFLICT: обе стороны
завершают партию явно, а не продолжают по разным правилам.

**Принудительная синхронизация (кнопка во всех играх).** Кнопка «⟳ Синхр»
зовёт `SessionManager.requestSync`: обычный `SYNC_REQ` (с хвостом журнала,
никаких новых MsgType), но через приоритетный путь транспорта
`SessionTransport.sendNow` — отдельный запуск на IO-пуле минует общую
очередь `sendAsync`, поэтому запрос уходит раньше уже накопившихся
отправок; повторы расписания канала после этого работают как обычно.
Ничего не блокируется и ни на что не ждётся; повторные нажатия быстрее
5 с игнорируются (кулдаун), чтобы зажатая кнопка не плодила дубли с
полными расписаниями ретрансмиссий.

**Журнал ходов и восстановление вместо конфликта.** Каждая сессия ведёт
канонический журнал (файл `journal-<sid>.json` в данных приложения;
**удаляется вместе с сессией**): индекс 0 — базовая точка (состояние движка
до первого хода; для морского боя — раскладка: она случайна, реплеем из нуля
невоспроизводится, поэтому снимок обязателен), далее события
`(тип ∈ {MOVE, SHOT, SHOT_RESULT}, абсолютная сторона, payload-байты)` с
локальным снимком/дайджестом после события и цепной FNV-суммой префикса
`chain_i = fnv(chain_{i-1} || тип || сторона || payload)`. Каноническая
часть (тип/сторона/payload) байт-в-байт одинакова у обеих сторон; снимки и
дайджесты — локальные (свои).

`SYNC_REQ` несёт хвост журнала в payload, `SYNC_RES` — свой хвост после
6-байтового ядра:

```
[u16 digest][u8 count] count × [u16 index][u32 chain][u16 digest]
≤ 12 записей (99 байт ≤ 200 байт под envelope)
```

Хвосты снимаются ДО начала обмена, и обе стороны на одинаковых данных
выполняют один и тот же детерминированный алгоритм (`reconcile`):

1. **Пир впереди** (его записи сверх моего префикса, цепь на префиксе
   совпала) — пир сам досылает свои записи; я возвращаю состояние к
   вершине своего журнала (это снимает, например, локальный сброс
   `pendingShot` по таймауту) и жду досылку;
2. **Я впереди** — досылаю свои записи из журнала («дырка» в принятом у
   пира); если пир повторно отвергает ту же запись — это уже настоящий
   раскол, переход к откату;
3. **Цепи в общем окне разошлись** — проверенный откат: иду вниз от общего
   префикса и беру первую запись, чей снимок воспроизводит дайджест,
   подтверждённый пиром (промежуточные «внутри транзакции» точки —
   выстрел без результата в морском бое — дайджестом не подтверждаются и
   пропускаются). Откат: восстановить снимок, урезать журнал, забыть
   игровые кадры в расписании повторов (`ReliableChannel.forgetGameFrames`,
   иначе повтор отброшенного хода снова развёл бы партию), уведомить
   игроков (`SessionEvents.onSessionRecovered` → строка
   «↺ … откат к ходу №N, партия продолжена»);
4. **Проверить не удалось** — у пира нет хвоста (повреждённый или пустой
   журнал), общий префикс не найден в окне или снимок не подтверждён — прежнее
   поведение: `SYNC_CONFLICT` завершает партию.

Досылка идёт обычными надёжными кадрами с новым seq — дедуп, piggyback и
расписания работают как обычно. Состояние `engineState` сессии остаётся
истиной локального состояния: если журнал на диске с ним не совпал (сбой
между двумя записями), расхождение логируется, верим `engineState`; журнал
продолжает сверяться по хвостам.

**Лечение зависшего выстрела.** Если `SHOT_RESULT` потерян безвозвратно
(повторы не доходят), движок висит вне покоя и сравнение
дайджестов заблокировано — так в поле (16.10) обе стороны зависали во
взаимном `pendingShot` и выхода из партии не было. Сессионный слой ведёт
таймер с момента выстрела (`pendingShotSinceMs`; после рестарта окно
стартует заново от первого тика): через `PENDING_SHOT_TIMEOUT_MS` (300 с)
он сбрасывает `pendingShot` — сброс **не входит в дайджест** — забывает
игровые кадры в расписании (`forgetGameFrames`: непОДТВЕРЖДЁННЫЕ теперь
живут вечно, а повтор отброшенного хода снова развёл бы состояния) и
отправляет `SYNC_REQ` (с хвостом журнала). Дальше сверка по журналу (см. выше): пир,
у которого результат есть, досылает его; поздний `SHOT_RESULT` после сброса
**спасается** — `rescueLateShotResult` по журналу узнаёт координату моего
выстрела, восстанавливает состояние на момент выстрела и применяет
результат по-честному: потерянный результат исцеляется без конфликта.
Досылка невозможна (у пира нет журнала) — прежние два исхода:
дайджесты разошлись → `SYNC_CONFLICT`, обе стороны завершают партию;
сошлись (SHOT до пира так и не дошёл) → партия продолжается. Ответ
`SYNC_RES` приходит мимо порядка (секция 3), дырка в `rxNext` его не
задерживает. В закрытой (`closed=true`) или неактивной сессии
таймер копится, но не лечит: исцеление происходит сразу после открытия,
фонового трафика нет.

## 5. TCP-мост: presence и эфирный путь

Игровой трафик идёт через локальный «Mesh Bridge» форка Meshtastic-Android
(`127.0.0.1:8090`, plain TCP). Мост транслирует payload каждого кадра
broadcast'ом в выбранный LoRa-канал как пакет со своим portnum
(настраивается в форке; дефолт 69 SIMULATOR_APP) и рассылает обратно
всем TCP-клиентам.

- **`want_ack = false` — намеренно.** Стоковый TAK-мост слал broadcast с
  `want_ack=true` (дефолт `DataPacket`), и firmware ретрансмитила каждый
  кадр до 4 раз (`NUM_RELIABLE_RETX`, ×4 к эфирному времени; на SF12
  ~12.5 с на непрошедший кадр). Множитель снят: вся надёжность — на нашем
  протоколе (секция 3);
- portnum настраивается в форке; дефолт 69 — штатная константа enum
  `PortNum` (`SIMULATOR_APP`): любой portnum из констант enum protobufs
  (41 шт.) проходит TX → firmware → RX без патчей protobufs; в приложении
  и прошивке никем не потребляется, конфликтов с чужим трафиком не
  ожидается. **Оба телефона обязаны использовать одинаковый portnum**
  (MeshGames его не видит и сверить не может — это настройка форка на
  каждом устройстве);
- presence (маркер готовности/занятости) шлётся при подключении, при смене
  активных сессий и периодически — с настраиваемой пользователем
  периодичностью **5..30 минут** (по умолчанию 10; каждый маркер —
  отдельный эфирный пакет, реже = меньше нагрузка на LoRa-канал):
  wrapper `[clientId u32 LE][0]`, body
  `[0x50][ver=1][busy u8][nameLen u8][name UTF-8 ≤ 32]`
  (имя обрезается по 32 байтам без разрыва UTF-8-последовательности);
- **HELLO (мост → клиент, служебный кадр идентичности):** при подключении
  TCP-клиента и при появлении/смене информации о ноде мост присылает

  ```
  [u32 len LE][u32 loraFrom=0][u32 loraTo=0][u32 from=0][u32 to=0][body…]
  len = 16 + body.size
  body = [0x49][ver = 1][nodeId u32 LE][nameLen u8][name UTF-8 ≤ 32]
  ```

  `nodeId` — номер СВОЕЙ ноды (`myNodeNum`), `name` — longName ноды
  (fallback shortName; пусто → `nameLen = 0`). Нулевой LoRa-заголовок
  обязателен: старый APK игнорирует неизвестный magic-байт `0x49`, но
  кадр короче минимума (`len < 17`) счёл бы повреждённым и разорвал
  соединение. Отсутствие HELLO (старый форк без доработки) — норма,
  клиент работает как раньше. Спецификация доработки форка —
  `meshbridge-hello-prompt.md`;
- бюджет: wrapper ≤ 220 байт — envelope типичного игрового кадра
  (заголовок ≤ 12 + payload) укладывается с запасом;
- keepalive: клиент шлёт ping (`len=0`) каждые 15 с; обрыва TCP-тишина
  не означает (тишина в эфире — норма), реконнект происходит только по
  ошибке записи или EOF, бэкофф 2..30 с.

### Идентичность игрока: clientId и имя

- в pref'е `tak_client_id` уже есть id (обновление приложения) — он
  **сохраняется навсегда**: смена сломала бы узнаваемость телефона у
  соперника и ссылки сохранённых сессий;
- свежая установка/переустановка стартует на временном id с флагом
  `tak_client_id_pending` (переживает рестарты); первый HELLO от моста
  закрепляет `id = nodeId` ноды и снимает флаг — переустановка приложения
  больше не меняет игрока; без HELLO (старый форк) временный id живёт
  и сохраняется как раньше;
- имя игрока: явно заданный `player_name` → имя ноды из HELLO →
  заглушка `Игрок-XXXX`. Миграция id и смена дефолтного имени сразу
  переобъявляют presence (`announce(force=true)`).

Надёжная доставка, валидация ходов и возобновление (секции 3, 7) от
транспорта не зависят — для `game/` он прозрачен.

## 6. Payload MOVE по играм

| Игра | Payload |
| --- | --- |
| Крестики-нолики | `[клетка]` (0..8) |
| Шахматы | `[from, to, promo]`: 0..63 (0 = a8), promo: 0 нет, 1 ферзь, 2 ладья, 3 слон, 4 конь |
| Шашки | `[n, sq0, sq1, …]`: n — число площадок; простой ход — 2 площадки (откуда, куда), взятие — откуда и все площадки приземления по порядку (квадраты побитых принимающая сторона вычисляет по доске: формат один, легаси-вариант «откуда, побита, площадка…» удалён) |
| Морской бой | MOVE не используется: SHOT `[coord]` → SHOT_RESULT `[coord, res]` |
| Балда | слово `[0x01][cell][letter][pathLen][path…]` или компактное с дельта-путем `[0x41][cell][letter][pathLen][startCell][packedDirs…]` (2 бита на направление N/S/W/E); спорное слово `[0x81]` / `[0xC1]`; пропуск `[0x02]`; вердикт `[0x03][verdict]` (1 принять, 0 отклонить) |
| Дурак | атака/подкидывание `[0x01][card]`, бить `[0x02][card]`, беру `[0x03]`, хватит `[0x04]`; `card = rank*4 + suit` (0..35: rank 0 = 6 … 8 = Т, suit 0 = ♦, 1 = ♣, 2 = ♥, 3 = ♠); подкидывание — по номиналу любой карты захода (см. «Дурак» ниже) |

### Балда: спорное слово и вердикт

`letter` — код буквы 1..33 (А=1 … Я=33); «ё» в кадрах и на поле не живёт —
канон «е» = 6, код 7 отвергается на обеих сторонах);
`path` — клетки змейки (0..24, соседние по ортогонали, без повторов,
обязательно содержит `cell`). Жёстко валидируется только структура:
слово, не найденное в словаре принимающего, уходит как `0x81`.

Спор симметричен обеим сторонам и не меняет очередь хода: слово ложится
на поле условно, `turn` остаётся у инициатора. Вердикт даёт только
НЕ двигавшая букву сторона и шлёт его кадром MOVE вне очереди хода
(прецедент `SHOT_RESULT`, новых MsgType нет) — повторы вердикта идемпотентны
и закрываются journal-resend/вечными повторами:

- **принять** — очки инициатору (длина слова), оба счётчика пропусков
  обнуляются, очередь переходит к ответившему;
- **отклонить** — буква снимается с поля, очередь остаётся у инициатора.

Три пропуска подряд одной стороной — её поражение (`GAME_OVER`,
причина `THREE_PASSES`); поле заполнено — сравнение очков (`BOARD_FILLED`),
равенство = ничья. Стартовое слово (средняя строка) — детерминированная
функция sid от словаря: обе стороны обязаны выбрать его одинаково.
Повторять нельзя **никогда** уже сыгранные слова — и стартовое тоже
(жёсткое отклонение на обеих сторонах ещё до отправки кадра).

Проверка словаря с парными буквами: е/ё, и/й, ь/ъ считаются одними и теми
же — если точной формы слова нет, движок перебирает варианты замен по
позициям с этими буквами (≤ 2^10, чистая детерминированная функция — обе
стороны принимают слово одинаково). На поле и в таблице выбора букв —
канон: е, и, ь (е-код нормализуется и при приёме, как раньше); повторы
слов сверяются по канонической форме (`canonical`: е/ё, и/й, ь/ъ взаимозаменяемы —
слова «майка» и «маика», «полет» и «полёт», «подъем» и «подьем» считаются
одним словом и повторно сыграны быть не могут).

### Дурак: скрытая информация через детерминизм

Кадры несут только действия — раздача в эфир не идёт. Обе стороны
считают одну и ту же раздачу из сида `sessionId` (xorshift32 +
Fisher–Yates — прецедент: стартовое слово балды): руны, козырь (нижняя
карта колоды, виден обеим сторонам) и порядок добра идентичны;
скрытость — только уровень UI (чужая руна не рисуется). Дайджест,
restore и SYNC_CONFLICT работают как в остальных играх.

Канон правил (закреплён движком, менять болезненно): 36 карт, по 6 на
раздаче; начальный атакующий — у кого младший козырь (равенство —
младшая карта вообще); стол захода **накапливает пары** «атака/бой»
до 6 — свежий заход открывается любой картой (`[0x01][card]`), подкидывание
идёт тем же кадром по номиналу ЛЮБОЙ карты захода (и атаки, и боя), только
от атакующего, пока атак < 6 и защитнику есть чем ответить (его рука не
пуста); бой — той же масти старше либо козырь, защитник бьёт последнюю
(небитую) карту; бой 6-й атаки закрывает заход сам (авто-бито, без
«хватит»); «хватит» легален, когда все карты забиты (→ «бито»: весь заход
в сброс, оба добирают до 6, первым — атакующий, роли меняются местами —
атакующий следующим становится защитник), либо при взятии защитником
(атакующий завершает подкидывание вдогонку); взятие (`[0x03]`) — защитник
объявляет о намерении забрать карты (`taking=true`), атакующий получает ход
для подкидывания вдогонку карт совпавших со столом номиналов (до количества
карт на руке защитника и лимита 6 атак), после чего атакующий отправляет
«хватит» (`[0x04]`); берущий ЗАБИРАЕТ ВСЕ карты захода (атаку и бой),
атакующий остаётся (защитник теряет ход), добор тот же; колода кончилась —
в точке бито/взятия: игрок без карт вышел, последний с картами — дурак
(`GAME_OVER`, причина `LAST_WITH_CARDS`, winner — вышедший), оба вышли сразу —
ничья (`BOTH_OUT`).

Формат состояния движка — `DurakEngine.STATE_VERSION = 4` (стол — списки
`attacks`/`beats` + байт `taking`); состояние версии 3 декодируется с
`taking=false`; состояние прежней версии (до подкидывания, байт 0 =
фаза 0..2) отклоняется при restore — партия создаётся заново из sid
(раздача детерминирована, у обеих обновлённых сторон идентична).

## 7. Возобновление прерванной партии

`GameSession` (движок + nextSeq/rxNext/unacked + флаги приглашения) пишется
в JSON-файл при каждом изменении (атомарно: tmp + rename). После рестарта
`SessionManager.restore()`:

- сессии со статусом CANCELLED/DECLINED не восстанавливаются (их осиротевшие
  журналы ходов убираются с диска);
- движок восстанавливается из `engineState`, канальные счётчики — из полей
  сессии; неподтверждённые кадры продолжают ретранслироваться;
- журнал ходов сессии загружается вместе с ней (сверка «последних ходов»
  работает и после рестарта);
- если сессия была в INVITING/INVITED — приглашение можно переиграть;
  если ACTIVE — игра продолжается с того же хода.

## 8. Широковещательная статистика и автономный бот-сервер

При завершении партии (победа, поражение, сдача, ничья) обе стороны (или инициатор завершения)
передают в канал широковещательный кадр статистики `STAT_BROADCAST`:

```
[len = 23 LE][u32 from LE][u32 to = 0 LE][body (15 байт)]
```

Тело кадра статистики `body`:
```
[0]     magic      = 0x53 ('S')
[1]     version    = 1
[2]     gameTypeId u8 (1..6)
[3..4]  sessionId  u16 LE
[5]     winner     u8 (0 = Side.A, 1 = Side.B, 2 = ничья)
[6]     reason     u8 (ResultReason.ordinal)
[7..10] playerA    u32 LE (clientId игрока со стороной A)
[11..14] playerB   u32 LE (clientId игрока со стороной B)
```

Кадр занимает ровно 15 байт (23 байта с wrapper'ом), не требует подтверждений и свободно
принимается всеми нодами в эфире.

### Сервер статистики и бот (`bot_server`)
- Автономный демон `bot_server` подключается напрямую к ноде Meshtastic (порт 4403, Protobuf)
  или мосту, заменяя собой MeshBridge, и слушает portnum игровых кадров (дефолт 69 SIMULATOR_APP);
- При приеме кадра `0x53` сервер сохраняет результат в базу `bot_data/stats.json`, дедуплицируя
  записи по ключу `(sessionId, gameTypeId, playerA, playerB)`;
- Имена игроков берутся из периодических presence-кадров `0x50` и HELLO `0x49`;
- Команда консоли `table` (`t`): выводит форматированную таблицу рейтинга игроков, винрейт,
  число побед/поражений/ничьих и последние партии;
- Команда в канале Meshtastic `!table` / `!таблица`: при получении текстового сообщения
  (`PortNum.TEXT_MESSAGE_APP = 1`) от любого узла сервер вещает в канал краткую сводку топ-игроков,
  строго соблюдая лимит $\le 100$ символов кириллицы / $\le 200$ байт UTF-8.
- Фильтрация шума: сервер отфильтровывает эхо собственных пакетов (`from == myId`),
  а также игнорирует не адресованные ему игровые кадры (`to != 0 && to != myId`), защищая эфир и ресурсы.
